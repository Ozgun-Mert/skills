# Security gate (Phase 6)

The gate runs after the backend wave, in its own fresh worker (`security`), and is verified by
the orchestrator. Its #1 job: **no user can read, change, delete or even detect another user's data
unless the spec's access-control matrix says it is shared.**

## 1. Access-control matrix (written in Phase 3, in `mnm/spec.md`)

One row per resource × action. Columns are the actors:

| Resource | Action | Owner | Shared member (role) | Other user | Other tenant's admin | Anonymous | Admin | Ownership rule |
|---|---|---|---|---|---|---|---|---|
| deck | read | 200 | 200 (viewer) | 404 | 404 | 401 | 200 | `deck.owner_id = me OR me ∈ deck.shares` |
| deck | update | 200 | 403 (viewer) / 200 (editor) | 404 | 404 | 401 | 200 | owner or editor |
| deck | list | own only | shared with me | — | — | 401 | all | filter in query |

- **404** for "exists but not yours", so existence isn't leaked. **403** when the actor can see the
  resource but lacks the permission. **401** when not signed in.
- Drop columns that don't apply, e.g. no tenants → no "other tenant's admin".
- Every endpoint in `openapi.yaml` maps to at least one row.

## 2. Isolation test matrix (generated by the `security` worker)

For every endpoint × every actor column, there is one automated test that:
1. Seeds two (or three) users with their own resources, plus a second tenant when tenancy exists.
2. Calls the endpoint as the actor, against the other actor's resource id.
3. Asserts the exact status code from the matrix **and** that the body has no foreign data. For
   lists: the foreign ids are absent, and so are the counts and totals.

It covers the less obvious paths too:
- list/search/filter/sort/pagination params and `count`/`total` fields
- exports (CSV/PDF)
- file/media URLs (signed URL scoped and expiring, no guessable public paths)
- nested routes (`/decks/{deckId}/cards/{cardId}`: card belongs to the deck **and** the deck is
  yours)
- bulk endpoints
- GraphQL-style `ids[]`
- websocket subscriptions/rooms
- webhooks
- background-job results
- invite/share acceptance (token single-use, bound to the invitee)
- password reset/email change (token bound to the user)
- admin endpoints as a non-admin

Put them in `backend/tests/security/test_isolation*` (or the stack's equivalent), runnable by one
command that the report prints. The gate needs **every test passing**, and the test count must be at
least endpoints × applicable actors.

## 3. Review checklist (severity in brackets is the default)

**Access control**
- [Critical] Missing auth on a route that touches user data.
- [Critical] IDOR: an object fetched by id without owner/tenant scoping in the query.
- [Critical] Mass assignment: client can set `owner_id`, `role`, `tenant_id`, `is_admin`, `price`,
  `status`.
- [High] Lists/search leak foreign rows or counts.
- [High] Nested resource not checked against its parent.
- [High] Admin check done only in the frontend.
- [High] Client-sent user id or tenant id trusted (header, body, query).
- [Medium] 403 vs 404 leaks existence.

**Authentication & sessions**
- [Critical] Passwords not argon2id/bcrypt; plaintext or reversible secrets.
- [High] Session token not random enough, not hashed at rest, no expiry, no rotation on login, not
  invalidated on logout/password change.
- [High] Cookie missing `HttpOnly`/`Secure`/`SameSite`.
- [High] Reset/verification tokens reusable, unhashed, long-lived or not bound to the user.
- [High] OAuth without `state`/PKCE, or account linking by unverified email.
- [Medium] User enumeration through login/reset/signup messages or timing.
- [Medium] No brute-force protection on login/reset.

**Input & injection**
- [Critical] SQL/NoSQL injection: string-built queries, raw queries with user input.
- [Critical] Command injection, path traversal, SSRF (fetching user-given URLs without an allowlist
  and private-IP blocking), unsafe deserialization.
- [High] No input validation or size limits; unbounded pagination; ReDoS-prone regex.
- [High] Uploads: no type/size checks, served from the app origin with executable content types,
  user-controlled file names.

**Web**
- [High] CSRF on cookie-authenticated state changes (needs SameSite plus an Origin check, or
  tokens).
- [High] CORS `*` with credentials, or reflecting any origin.
- [Medium] Missing security headers (CSP, HSTS, X-Content-Type-Options, frame-ancestors,
  Referrer-Policy).
- [Medium] No rate limits on auth and write endpoints.
- [High] XSS: unescaped user content rendered as HTML (`{@html}`, `dangerouslySetInnerHTML`)
  without sanitizing.

**Data & secrets**
- [Critical] Secrets in code, the repo or frontend bundles (`NEXT_PUBLIC_*`/`PUBLIC_*` holding
  server keys).
- [High] Responses returning more than needed (password hashes, tokens, other users' emails).
- [High] Stack traces or SQL errors in responses.
- [Medium] Personal data, tokens or passwords in logs.
- [Medium] RLS not enabled on tenant/user tables (defense in depth) when Postgres is used.

**Business logic & money** (when present)
- [Critical] Prices/totals/discounts taken from the client.
- [Critical] Payment webhooks without signature verification or idempotency.
- [High] Race conditions on balances, inventory or one-time actions (needs transactions, row locks
  or unique constraints).

**Dependencies**
- [High] Known vulnerable dependencies (run `pip-audit` / `bun audit` or `npm audit` /
  `govulncheck`). Fix by upgrading.

## 4. Process for the `security` worker (put this in `securityprompt.md`)

1. Read `mnm/security-hotspots.json` (from `security_scan.py`), the spec's access-control matrix,
   the contract, and the backend files the hotspots point to. Then read the auth/session module and
   every route file. This piece is allowed to read all of `backend/**`.
2. Write `mnm/reports/security.md` with findings first (format below).
3. Write the isolation test matrix (§2) and the regression tests for each finding.
4. Fix every Critical and High. Fix Medium unless the fix needs a product decision; that becomes a
   question.
5. Run the full backend test suite, the isolation suite and the dependency audit. Print all three.
6. Rerun `security_scan.py`. Every remaining hotspot is marked in the report as false positive,
   with a one-line reason, or fixed.

Goal condition proof: isolation suite output (N passed, 0 failed, N ≥ endpoints × actors), full
suite green, audit clean (or only accepted Low items listed), report printed with 0 open
Critical/High.

## 5. Report format (`mnm/reports/security.md`)

```markdown
# security: <achieved|partial>
## Summary
Critical 0 · High 0 · Medium n · Low n (open) — fixed: C n, H n, M n
Isolation matrix: <N> tests (<endpoints> endpoints × <actors> actors) — all pass
Audit: <tool> — <result>
## Findings
| ID | Severity | Status | File:line | Problem | Fix | Regression test |
## Hotspots reviewed
| Hotspot | Verdict (fixed / false positive: reason) |
## Answers applied
## Assumptions taken
```

## 6. Orchestrator verification (don't skip)

1. Run the isolation suite command and the audit command yourself. Read the counts.
2. Read only the handlers listed in Critical/High findings, plus 2 random endpoints from the
   matrix. Confirm the scoping is in the query and the actor comes from the session.
3. Check that the frontend doesn't expose server secrets: grep `NEXT_PUBLIC_|PUBLIC_|VITE_` for key
   or secret names.
4. Any doubt → `--resume` the security worker with the exact concern. The gate passes only on
   output you've seen yourself.

After QA (which may touch backend code), rerun the isolation suite once more before the final
report.
